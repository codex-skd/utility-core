<h2>v1.11.12 - Recipe Selector Fixed</h2>

<h3>Fix</h3>
<ul>
<li><strong>Recipe selector no longer reverts to the first option</strong>: Selecting an alternative recipe from the crafting selector briefly showed the chosen result, but the output immediately snapped back to the first recipe. The server only updated the <em>remote</em> slot (the client display copy) without writing the real crafting result, so <code>broadcastChanges()</code> detected the mismatch and re-sent the first recipe's output on the next tick. Now the server also writes the actual result slot (<code>ResultContainer</code>) and sets <code>recipeUsed</code>, so the selection sticks.</li>
<li><strong>Selector re-enabled by default</strong>: <code>enableCraftingRecipeSelector</code> is back to <code>true</code> now that the server-side issue is resolved.</li>
</ul>

<h3>Technical Changes</h3>
<ul>
<li><code>SelectRecipePacket.handle()</code> — writes the selected output into the real result slot and the remote slot, and sets <code>recipeUsed</code> on the <code>ResultContainer</code>.</li>
<li>Debug logging added with the <code>[RecipeSelector]</code> prefix (INFO level) to trace clicks, sync packets and server selection state.</li>
</ul>

<h3>Notes</h3>
<blockquote>If the selector still misbehaves, send the <code>[RecipeSelector]</code> log section (placing items + clicking the 2nd option) for diagnosis.</blockquote>
